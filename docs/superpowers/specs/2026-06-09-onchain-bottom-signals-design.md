# On-Chain Bottom Signals Design

## Goal

Add an on-chain "bottom signal" scoring system inspired by a third-party dashboard: five signals scored 0-20 each, a composite 0-100 score with zone classification, and a historical backtest (trigger segments + accuracy matrix) that shows how the composite score performed near past cycle bottoms. Deliver it as a self-contained dashboard page generated by the existing daily pipeline, plus a summary card on the main dashboard.

## Background

The reference site (a third-party dashboard, "BTC 底部信号看板") is a daily-regenerated static page, architecturally identical to this project. Its five signals are: S1 price vs LTH/average/STH holder cost basis, S2 MVRV deviation from its historical mean in sigma units, S3 relative unrealized loss, S4 30-day realized-cap net change, S5 Fear & Greed Index. It cites Glassnode (paid) as its data source, but its S5 values match alternative.me exactly and its history starts 2018-02-01, the inception date of the alternative.me index.

Verified free data path for this project:

- `https://api.bitcoin-data.com` (BGeometrics) covers every on-chain metric needed: `/v1/lth-realized-price`, `/v1/sth-realized-price`, `/v1/realized-price`, `/v1/mvrv`, `/v1/supply-loss`, `/v1/realized-cap-change-30d`. Free tier: no token, 10 requests/hour, 15/day, history limited to the most recent 4 years (verified: pre-window queries return `[]`).
- alternative.me provides full Fear & Greed history (2018+) for free; a provider already exists in this repo.
- CoinMetrics Community no longer serves realized-cap metrics for free (verified: 403).

Accepted consequences (user decisions):

- Pure free tier; no paid backfill. The composite series therefore starts ~2022-06 and the backtest covers two cycle bottoms (2022-11-21, 2024-09-06) instead of the reference site's five.
- Fetched history is accumulated in a repo CSV so local history grows beyond the 4-year API window over time.
- S3 substitutes supply-in-loss percentage (share of circulating supply whose last on-chain move was above the current price) for the reference site's value-weighted relative unrealized loss, which is not freely available. Same bottom semantics: ~0-2% at bull tops, 50%+ at bear bottoms.

## Requirements

- Fetch six bitcoin-data.com series and full Fear & Greed history during the daily pipeline run, at most once per day, staying within free-tier limits (sequential calls spaced >= 7 s, <= 7 requests per run).
- Persist merged on-chain history to `docs/data/onchain_metrics.csv`; re-fetched dates overwrite, history is never truncated, writes are atomic (temp file + replace), matching existing persistence patterns.
- Compute S1-S5 scores (0-20 each, formulas below), composite (0-100), and zone for every date where all five inputs exist.
- Zones match the reference site: < 60 Watch, 60-70 Mildly Undervalued, 70-80 Undervalued, >= 80 Extremely Undervalued.
- Backtest: extract trigger segments for threshold {60, 70, 80} x minimum consecutive duration {1, 3, 7} days; per segment record start/end dates, length, start price, segment minimum price, and minimum price within 90 and 180 days after segment end; build the 3x3 accuracy matrix where a segment is a hit if its minimum price <= assigned cycle bottom price x 1.3 (assigned bottom = the cycle bottom date nearest the segment midpoint).
- Cycle bottoms are a code constant, initially `[("2022-11-21", 15797.53), ("2024-09-06", 53914.82)]`, extensible.
- Render `docs/charts/bottom_signals.html` via a Jinja2 template: hero (current price, 24h change, distance from ATH, composite gauge SVG with zone label and one-line guidance), five signal cards plus an MA120/MA200 reference card (each card: status label, score, score bar, position scale with marker, current raw values, ~90-day score sparkline), main Plotly chart (log price + composite score on right axis + trigger-segment shading + cycle-bottom dashed lines, with client-side threshold/duration toggles backed by embedded precomputed JSON), trigger-segment detail table, accuracy matrix, methodology notes (S3 substitution, 4-year window, full-sample sigma caveat, bitcoin-data.com and alternative.me attribution), and a not-investment-advice disclaimer.
- Page language is English, styling follows the existing site's visual language, layout is responsive (desktop + mobile).
- Page loads plotly.js from the CDN (pinned version) instead of embedding ~3.5 MB; the page must contain no API calls and no secrets at runtime.
- Write `docs/charts/bottom_signals_info.json` (date, composite, zone, per-signal scores/status, advice line) and render a summary card on `docs/index.html` near the top status area that fetches it and links to the full page (same pattern as `oi_quadrant_info.json`).
- Add an "On-Chain Bottom Signals" section to `daily_report.json`; the existing "Supplemental Bottoming Signals" section (technical/sentiment proxies) remains unchanged.
- Any fetch failure degrades gracefully: pipeline continues with cached CSV data, the page shows its data date, other charts are unaffected. Honor `--strict-update` semantics consistently with existing fetchers.
- Support an optional `BGEOMETRICS_TOKEN` env var (sent as `Authorization: Bearer`) for a future paid upgrade; absent means free tier.

## Design

**Provider** (`src/whenshouldubuybitcoin/providers/bitcoin_data_com.py`). One function per metric plus a shared `_get(path, params)` helper handling token, retry-with-backoff, 7 s spacing, and timeouts. Responses are JSON arrays of per-day objects; exact field names are captured as fixtures from one probe call per endpoint at implementation start, and parsing is pinned to those fixtures in unit tests. Incremental fetches pass `startday` = last cached date minus 7 days (late revisions); first run fetches the full free window. A freshness guard skips all network calls when the CSV already contains data for today or yesterday (UTC daily series lag), protecting the 15/day budget from repeated local runs.

**Fear & Greed history**: extend `providers/alternative_me.py` with `fetch_fear_and_greed_history()` (`?limit=0`), returning date-indexed integer values.

**Persistence**: `docs/data/onchain_metrics.csv` with columns `date, lth_realized_price, realized_price, sth_realized_price, mvrv, supply_loss_pct, realized_cap_change_30d_usd, fear_greed`. Merge = outer join on date, new data wins on overlap, sorted ascending, atomic write.

**Scoring** (`src/whenshouldubuybitcoin/bottom_signals.py`, pure functions over pandas series). All scores clamp to [0, 20] and interpolate linearly between anchors:

- S1 (holder cost): anchors on price P vs lines LTH < AVG < STH, interpolated in log space: P >= 1.2 x STH -> 0; P = STH -> 5; P = AVG -> 10; P = LTH -> 15; P <= 0.8 x LTH -> 20.
- S2 (MVRV deviation): d = (mvrv - mean) / std over the full available sample. d >= +2 -> 0; d = 0 -> 8; d <= -1.5 -> 20.
- S3 (supply in loss): d = (supply_loss_pct - mean) / std, full sample. d <= -1 -> 0; d = 0 -> 6; d = +0.5 -> 10; d >= +2 -> 20.
- S4 (capital net change): score = 20 x (1 - historical percentile of the 30-day realized-cap change). Self-calibrating; the reference site's divergence logic is out of scope.
- S5 (Fear & Greed): v <= 10 -> 20; v >= 75 -> 0; linear between.
- Composite = S1 + S2 + S3 + S4 + S5, computed only for dates with all five inputs; sigma/percentile statistics are computed once over the full available sample — not expanding windows — so early dates score with the same statistics as recent ones (same approach as the reference site; the look-ahead caveat is stated on the page). If the sample holds fewer than 180 observations, sigma/percentile-based scores and the composite are null.

**Backtest** (same module): boolean series `composite >= threshold` -> strictly consecutive runs -> keep runs with length >= duration. Forward windows are relative to segment end. Output structure mirrors the reference site's embedded `TRIG` JSON: `{threshold: {duration: [segments]}}` so the page's toggle JS stays trivial.

**Rendering**: Jinja2 template at `src/whenshouldubuybitcoin/templates/bottom_signals.html.j2`, rendered by a new `generate_bottom_signals_page()` called from `main.py` after metrics are computed, written atomically like other charts. Gauge arc paths, scale-bar marker positions, and sparkline polylines are computed in Python helpers; the only client-side JS is the threshold/duration toggle + Plotly relayout, operating on embedded JSON. The summary card on `index.html` is populated by a small fetch of `bottom_signals_info.json` with graceful absence handling (card hidden if the file is missing).

**Pipeline wiring** (`main.py`): fetch step runs before chart generation, wrapped so failures log a warning and fall back to the existing CSV; page generation runs with whatever data is present and stamps the data date.

## Testing

- Provider: parsing against recorded response fixtures; retry/backoff and freshness-guard behavior with mocked HTTP.
- Persistence: merge idempotency, overlap overwrite, atomic write, schema stability.
- Scoring: anchor-point exactness, monotonicity, clamping for each of S1-S5; composite null handling when inputs are missing or below the 180-observation guard.
- Backtest: segment extraction on synthetic series (gaps, exact-threshold days, duration filtering), forward-window stats, accuracy matrix on constructed scenarios.
- Acceptance: with live data, today's composite lands in the Watch zone with S5 = 20, S2 ~ 13-15, S1 low — same ordering as the reference site on the same day; segment table and accuracy matrix populate for the 2022-11 bottom.
- Browser verification of `bottom_signals.html` and the index summary card, desktop and mobile, per AGENTS.md.

## Out of Scope

- Feeding the composite score into DCA strategy sizing (future candidate, alongside AHR999).
- Divergence-based S4 refinement.
- Paid BGeometrics/Glassnode tiers and pre-2022 backfill.
- Chinese localization of the new page.
